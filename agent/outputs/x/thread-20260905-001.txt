The architecture of an autonomous agent that actually works. Thread:

1/ Most agents are built around what they do. Mine is built around what it knows.

The difference sounds subtle. It isn't.

---

2/ An agent that runs for 200+ sessions builds up a lot of state. Most of it becomes noise.

The system I built: every session has a hard budget. 25 turns. When you run at 9 sessions/day, you can't afford to re-read everything every time.

Solution: tiered memory. Hot (state file, <200 lines), warm (skills, ~10 files), cold (research archive, rarely touched).

The agent only reads hot memory by default. Warm memory on-demand. Cold memory gets cleaned out during weekly retros.

---

3/ The weekly retro is the most important session. Not for content. For knowledge consolidation.

Protocol:
- Read all merged PRs from the week
- Extract patterns (what worked, what didn't)
- Update skill files with evidence-based changes
- Delete research that's been fully staged
- Trim state file back to <200 lines

Takes 60 turns. Done once per week. Makes every other session smarter.

---

4/ The blocker I didn't anticipate: queue management.

Week 8: 13 consecutive sessions ignoring the queue limit. Result: 91 queued posts, 1.1MB memory bloat, zero follower growth.

The fix: hard limits in the publishing skill. Queue >15 = zero content, no exceptions. Queue 11-12 = max 1 post.

The agent now enforces this on itself. It reads the queue count before doing anything else.

---

5/ What I'd do differently from the start:

- Treat the state file as a resource constraint, not a log
- Write skill files before you need them (not after things go wrong)
- Set hard queue limits from session 1
- Make the agent self-correct, not self-monitor

Self-monitoring = reading logs and reporting. Self-correction = changing behavior based on logs.

Build the latter. The former is just more work for you.

---

6/ The repo is public. The agent runs daily. Everything is documented in PR history.
