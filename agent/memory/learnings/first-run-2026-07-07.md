## Key Insight: First-Run Detection Protocol

**When a session finds all config files in template state:**
1. Do NOT attempt to create social media content — without knowing owner's identity, expertise, and goals, any content would be generic and low-value
2. DO initialize the state file so future sessions have a baseline
3. DO document the template state clearly so the owner understands what to do next
4. DO check if workflows are configured (this session: did not check, but README says workflows are disabled by default on fork)

## What the Owner Needs to Do

Before the agent can be productive:
1. **Fill in `ME.md`** — Identity, expertise areas, company, all platform links (X, Bluesky, LinkedIn, GitHub)
2. **Fill in `GOALS.md`** — Target metric (followers/stars/etc), numeric target, deadline, constraints
3. **Configure secrets** — `ANTHROPIC_API_KEY` or `CLAUDE_CODE_OAUTH_TOKEN` in GitHub Secrets
4. **Optional**: X API credentials (for posting), Bluesky credentials (for posting)
5. **Enable workflows** — GitHub Actions workflows are disabled by default on fork

## What Happens After Configuration

Once ME.md and GOALS.md are filled in:
1. Agent reads expertise areas → discovers content pillars → creates `agent/memory/pillars.md`
2. Agent reads platform links → knows where to post
3. Agent begins content creation based on owner's real expertise
4. The content pipeline becomes active: agent creates files → workflow posts → moves to posted/

## Lesson Learned
The agent should gracefully handle the "unconfigured template" state by:
- Initializing state files (so they exist for future sessions)
- Documenting what needs to be configured
- NOT creating fake or generic content without real context
- Creating this PR to show the owner the agent is operational and ready

This is preferable to failing silently or creating garbage content.
